# T003-B — Atomic fail-closed arm hold transitions

## Question and scope

Does each invalid-input condition freeze the last arm target without a
lower-body/base command, and what joint velocity/acceleration/torque transient
does that *single* condition produce? The cases are intentionally separate;
their peak metrics must never be aggregated into a nominal smoothness value.

## Execute one case per run

```bash
conda run --no-capture-output -n unitree_sim_env \
  python scripts/teleop/run_r1_t003_trajectory.py --case-id deadman --headless

conda run --no-capture-output -n unitree_sim_env \
  python scripts/teleop/run_r1_t003_trajectory.py --case-id timeout --headless

conda run --no-capture-output -n unitree_sim_env \
  python scripts/teleop/run_r1_t003_trajectory.py --case-id sequence --headless
```

The commands allocate, respectively, `t003_b_deadman_`, `t003_b_timeout_`, and
`t003_b_sequence_` run IDs. Each config has exactly one 0.5-s injection at the
declared active trajectory time. The case passes its verification only when the
expected hold reason is observed and lower-body/base dispatch remains zero;
smoothness remains a measured outcome, not an assumed pass condition.

Each case has the same nominal target trace and one 0.5-s hold at active time
2.0 s. The observed acceleration peak is **10.12 rad/s²** in each safety case,
against 1.60 rad/s² in the separately measured nominal case. The current
freeze-in-place behavior therefore achieves the declared hold property, but
creates a measurable transition transient. This is a direct observation, not a
claim that the safety behavior is acceptable for hardware.
