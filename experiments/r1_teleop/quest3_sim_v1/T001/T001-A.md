## Question and criteria

Can a connected Quest deliver pose and controller telemetry to the host's Vuer
endpoint while the operator moves the headset and controllers?

The criteria declared before execution are: the endpoint starts, at least one sample reports
`motion_data_ready: true`, and at least 30 samples after that event carry finite
4x4 pose matrices.

This protocol is capture-only. It is not an R1 command bridge, a simulator sink
test, a calibration, an IK test, or a hardware test. Every recorded sample is
vendor transport telemetry: it is not an `R1TeleopCommand` and must not be sent
to a simulator or robot. No data inside the capture window is an inconclusive
connection result, never a synthetic success.

## Execution

Run from the repository root. The operator opens the printed HTTPS URL in Quest
Browser, accepts the certificate, **enters the immersive WebXR session**, and
then moves the headset and controllers.

```bash
conda run --no-capture-output -n tv python scripts/teleop/capture_quest_transport.py \
  --host-ip <host-ip> --duration-s 120 \
  --cert-file <cert.pem> --key-file <key.pem> \
  --output-dir experiments/r1_teleop/quest3_sim_v1/T001/runs/t001_a_<run-id>
```

Entering VR is the step that matters. `motion_data_ready` is set only when the
vendor wrapper receives a controller or hand event, and those are emitted only
inside an immersive session. A loaded page produces samples that look valid but
carry wrapper defaults. If the operator prefers hand tracking, add
`--input-mode hand`.

Each run directory must be new. The runner refuses to overwrite one.

## Immediate outcome

**The declared criteria are met** by `t001_a_20260802_quest02`. The criterion
asked for at least 30 finite motion-ready samples after the first motion-ready
event; the run recorded 1,711, and no sample anywhere in the capture holds a
non-finite pose value.

The data is observed motion rather than a stuck vendor default. Among the
motion-ready samples there are 1,450 distinct head-pose matrices and about 1,527
distinct matrices per wrist, the right trigger spans its full 0.0–10.0 range, and
the right thumbstick takes 35 distinct values. The preceding failed run
`quest01` had zero motion-ready samples; the operator difference was entering the
immersive WebXR session before moving.

### Two caveats carried forward to T001-B

**The first ~7 s of motion-ready data are transport settling, not motion.**
Derived from the analysis below: before t=7 s the head position steps
discontinuously and peak head speed reaches 20.22 m/s, which no human head
produces; from t=7 s onward peak head speed is 1.18 m/s. Any velocity or
acceleration claim must exclude that opening window. The capture itself is still
valid — the criteria concern pose validity and motion-ready count, not
smoothness — but a downstream consumer that differentiates the whole trace will
read fictitious spikes.

**The deadman was held for only 64 of 1,712 motion-ready samples (3.7%).** That
is harmless here, because a capture emits no command and the trigger is recorded
only as telemetry. It matters at T001-B, where the deadman gates dispatch: an
operator who holds the trigger this rarely will produce a run that is almost
entirely `deadman_released` holds and cannot demonstrate the end-to-end path.

## Derived analysis

Kinematics are derived from the immutable capture into a separate directory, so
the evidence run itself is never rewritten:

```bash
MPLCONFIGDIR=/tmp/mpl conda run -n r1_env python scripts/teleop/plot_r1_quest3_telemetry.py \
  --input experiments/r1_teleop/quest3_sim_v1/T001/runs/<run-id>/transport_samples.jsonl \
  --output-dir experiments/r1_teleop/quest3_sim_v1/T001/runs/<run-id>/analysis/telemetry_kinematics
```

`analysis/telemetry_kinematics/` holds `telemetry_kinematics.png`,
`telemetry_kinematics.csv` and `analysis_summary.json` with the source SHA-256.
Samples recorded before the first `motion_data_ready` carry vendor defaults and
are dropped rather than differentiated into fictitious velocity; the summary
records that.

## Diagnosis for the next attempt

A capture whose head-pose matrix is identical across all samples had no live XR
session. Deriving that from `transport_samples.jsonl` is the cheapest check:

```bash
python3 -c "
import json,sys
rows=[json.loads(l) for l in open(sys.argv[1])]
print('samples', len(rows))
print('motion-ready', sum(r['motion_data_ready'] for r in rows))
print('distinct head poses', len({json.dumps(r['head_pose_matrix']) for r in rows}))
" experiments/r1_teleop/quest3_sim_v1/T001/runs/t001_a_<run-id>/transport_samples.jsonl
```

Thousands of distinct head poses mean the XR session was live and the problem is
elsewhere. One or two distinct poses mean the session never started.

## Data products and validity

Each run writes the shared contract records plus `transport_samples.jsonl`.
`status.json` carries `sample_count`, `motion_ready_sample_count` and
`motion_ready_finite_pose_sample_count`, and asserts `r1_command_emitted: false`
and `simulator_sink_called: false`.

A run is invalid evidence if the capture crashes, if `transport_samples.jsonl`
is absent, or if any command was emitted. Zero motion-ready samples is a valid
recorded result and stays in the inventory.
