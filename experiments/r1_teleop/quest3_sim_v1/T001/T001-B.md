## Question and criteria

Is the Quest to bridge to R1 simulator connection established, observed, and
does it fail closed when the connection is lost?

The criteria declared before execution require all of: an observed command applied to the simulator,
a deadman-release hold, a disconnect timeout hold, a reconnect, complete evidence
files, and zero base-velocity dispatches.

## Architecture

Two processes joined by a pipe, because the Quest vendor wrapper (`tv`, Python
3.10, `vuer`, no IsaacLab) and IsaacLab (`unitree_sim_env`, Python 3.11, no
`vuer`) cannot share an interpreter.

```
Quest --HTTPS/WSS--> quest_bridge.py --R1TeleopCommand JSONL--> run_r1_quest3_live.py
                          |                                            |
                   QuestCommandBridge          R1TeleopMapper -> SimulationOnlyAdapter -> HeadOnlyIsaacLabSink
```

Both processes run on one host, so `time.monotonic()` is a shared
`CLOCK_MONOTONIC` timebase and command age is measured directly rather than
estimated from an offset handshake. Each run records this in `clock_record.json`.

Fail-closed behaviour is layered. The bridge emits no command for a sample that
is not motion-ready or whose pose matrices are not rotations, so a dropped
session produces a receipt gap rather than a stale repeat. The mapper then
applies its own `command_timeout`, and the sink's hold re-issues the last
commanded head target rather than snapping to nominal, because a snap would be an
uncommanded fast motion exactly when the input became untrusted.

The Quest controller gate uses TeleVuer's digital trigger flag with a
fail-closed analog fallback. The wrapper defines `10.0` as released and `0.0`
as fully pressed; a finite in-range value at or below the declared
`--trigger-value-threshold` counts as pressed. The default is `5.0`. The bridge
records the threshold and every effective press/release transition together
with the raw digital and analog values. This addresses Quest Browser sessions
that deliver controller poses and analog pull depth while leaving the WebXR
digital trigger flag false.

Compatibility note: runs through `t001_b_20260802T113518Z` used the earlier
digital-only gate. They remain valid evidence for that recorded implementation,
but they do not validate the analog fallback. A new live run is required before
claiming this revised controller-input path passes T001-B or T007.

## Declared scope limits

- **Head joints only.** `head_yaw_joint` and `head_pitch_joint` are driven from
  the mapper's existing scalar outputs, so no IK runs. Arm and wrist targets are
  carried and recorded but withheld pending the arm/wrist IK method gate
  ("Gate M", T002). Runs record `arm_targets_withheld_count`.
- **Pelvis pinned.** The base is held in place. A run shows no locomotion or
  balance behaviour and is not evidence of either.
- **Self-collisions disabled**, as a declared deviation; see below.

## Findings established during implementation

These came from direct execution on this workstation and hold for every T001-B
run, and for the protocols that follow.

**Self-collisions mechanically block the R1 head joints.** With the project asset
configuration (`enabled_self_collisions=True` in `training/isaaclab/robot.py`), a
commanded head yaw of −0.5 rad produced no motion: after 1.5 s of simulated time
the joint sat at −0.0002 rad while IsaacLab reported a sustained −13.17 Nm
actuator torque against a 20 Nm limit. Joint limits are not the cause (±2.007
rad) and neither is actuator mapping. Two controls isolate it: with no targets at
all the robot falls and `head_yaw_joint` moves freely to −0.1718 rad; re-running
the identical target test with only `enabled_self_collisions=False` changed, the
joint tracks to −0.5000 rad. The runner therefore exposes
`--disable-self-collisions` and records `self_collisions_enabled` in the resolved
config. **This is a workaround, not a fix** — the R1 USD collision geometry
around the head and neck needs its own review.

**IsaacLab joint order is not the SDK joint order.** The articulation reports 26
joints with `head_pitch_joint` at index 8 and `head_yaw_joint` at 13, while
`joint_sdk_names` lists them last at 24 and 25. `IsaacLabArticulationHandle`
resolves by name and raises if a head joint is absent.

**Asset joint counts differ between simulators.** `assets/mujoco/unitree_robots/r1/R1.xml`
has 24 actuated joints and no head joints; `assets/R1.urdf` and `assets/R1/R1.usd`
have 26 including both head joints. MuJoCo cannot serve as this protocol's sink.

**Achieved rates are load-dependent.** With both GPUs busy, 50 Hz control was not
achievable. Decoupling rendering from physics raised the achieved control rate
from 4.4 Hz to 19.2 Hz, and making physics catch up to wall-clock brought the
simulated-to-wall ratio to 0.9997 at `--physics-hz 100 --control-hz 20`. Runs
record `achieved_control_hz`, `sim_to_wall_ratio`, `simulated_time_s` and
`wall_time_s`.

## Bridge defect found by these runs, and fixed

Four runs failed to record a disconnect. The cause was **not operator error**;
the disconnect was undetectable by construction.

`TeleVuerWrapper.motion_data_ready` **latches**. It is initialized false, set
true on the first controller or hand event, and never cleared — the vendor's own
docstring says "True after the first ... event is received". It therefore reports
"has ever delivered motion", not "is delivering motion now". The bridge's
disconnect test was `if not sample.motion_data_ready`, which can never fire again
once a session has started.

`t001_b_20260802T111348Z` recorded the consequence directly. The head pose was
**bit-identical for 5.9 s** (t=19.6 s to 25.4 s) while the bridge emitted **177
commands** with fresh timestamps. Six shorter frozen stretches in the same run
lasted at most 0.2 s, which is what genuine stillness looks like: real head
tracking never repeats a pose bit-for-bit.

This was a fail-closed hole, not merely a missing observation. Because the bridge
kept refreshing the command timestamp, the mapper's `command_timeout` could not
fire either, so a lost headset would have left the simulator tracking a frozen
pose indefinitely.

**Fix:** `BridgeConfig.max_pose_stale_s` (default 0.5 s). A pose that has not
changed for longer than that is treated as a lost session: the bridge emits
nothing, records a `disconnected` transition, and reconnects when the pose moves
again. The mapper's timeout then produces the `command_timeout` hold the
criterion asks for. The default is bounded by the measurement above — 0.2 s of
real stillness versus 5.9 s of removal — and matches `command_timeout_s` so both
fail-closed layers agree on what stale means.

Covered by `FrozenPoseDisconnectTests` in `tests/teleop/test_r1_live_bridge.py`,
including a replay of the recorded 5.9 s removal and the full
bridge → mapper → sink chain ending in a `command_timeout` hold.

Runs recorded before this fix cannot satisfy the disconnect criterion and are
retained as the evidence that found it.

## What the next run must add

Only the disconnect and reconnect criteria are outstanding, so a short run is
enough; the passing parts do not need to be re-earned at length. With the bridge
and runner started as below, the operator must:

1. enter VR, hold the right trigger, move the head — a few seconds is sufficient;
2. **leave the XR session or remove the headset for longer than the 0.5 s command
   timeout**, and stay out long enough for the hold to be recorded;
3. **re-enter VR** and move again, so the bridge records a second `connected`.

The run passes when `metrics.json` lists both `command_timeout` and
`deadman_released` in `hold_reasons`, and the bridge log records
`disconnect_count` of at least 1 and `connect_count` of at least 2.

## Operational notes learned from the recorded runs

**Do not hand-write run ids.** Both the runner and the bridge refuse to start
when their output directory or stop file already exists, so a reused id fails
before the headset is ever involved. `scripts/teleop/run_t001_b_pilot.py`
allocates one free `t001_b_<UTC stamp>` id and derives the evidence directory,
connection log and stop file from it, which is also the only way both processes
are guaranteed to agree on the id.

**Zero commands means no immersive session, not a network fault.** `quest02`
recorded 1,130 dropped samples and zero motion-ready while the headset was
associated with the access point the whole time. The bridge drops any sample that
is not motion-ready, and that flag is set only once an immersive WebXR session
delivers a controller or hand event. Opening the page is not enough.

When no command ever arrives, the sink records no hold at all — `quest02` has
zero sink events. That is correct rather than a missed fail-closed: with no
command there is no target to hold, and the simulator stays at its spawn pose.
Hold evidence requires a stream that starts and then stops.

## Execution contract

```bash
python3 scripts/teleop/run_t001_b_pilot.py --host-ip <host-ip> --duration-s 90
```

The launcher allocates the run id, prints the evidence directory and the stop-file
command, and starts both processes joined by a pipe. `--dry-run` prints the paths
and the two commands without starting anything. It is the only supported live
entry point: it stages the bridge log while IsaacLab creates the run and moves
that log to `bridge_connection.jsonl` before finalizing the immutable evidence.

The operator sequence must exercise every gate criterion: enter VR and hold the
right trigger while moving the head (end-to-end path); release the trigger
(`deadman_released` hold); leave the XR session (`command_timeout` hold on
disconnect); re-enter (reconnect).

## Data products and validity

Each run writes the shared contract records plus `raw_commands.jsonl`,
`targets.json`, `sink_events.json`, `sink_acknowledgements.json`,
`control_loop.json`, `metrics.json`, `clock_record.json` and
`simulator_view.mp4`, plus `bridge_connection.jsonl` when launched through the
managed T001-B entry point.

A run is invalid evidence if the runner crashes, if any of those is missing, if
`base_velocity_dispatch_count` is non-zero, or if no live Quest session was
present. A disconnect that produces a hold is an expected pass. A run whose
`sim_to_wall_ratio` is far below 1.0 is inconclusive for latency and hold-timing
claims, because the operator was watching a simulator that was not keeping up.
